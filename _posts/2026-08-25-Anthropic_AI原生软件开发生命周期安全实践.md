## 先说结论：安全体系必须跟着代码产能一起扩容

Anthropic 披露，公司的软件工程师如今每季度交付的代码量，约为 2021—2025 年阶段的 8 倍；Claude 编写了当前约 80% 的合入代码，其中超过一半由内部版本的 Claude Tag 完成合并。人类工程师的工作重心则逐渐转向设定目标、提供上下文、判断风险并承担最终责任。

这类变化带来的问题并不只是“代码更多了”。AI Agent 具有非确定性，能力还会随模型升级持续变化。原先依靠人工评审、定期扫描和少数安全专家把关的流程，很容易成为整个交付链路的瓶颈。

Anthropic 的做法可以概括成一句话：**不要只在流水线末端增加一次 AI 安全审查，而要围绕 Agent 重新设计整条软件开发生命周期。**

它主要防范三类威胁：

- Agent 被攻陷或遭受提示注入后，引入恶意代码变更；
- 供应链、依赖或外部资料被投毒，却被 Agent 当作可信输入；
- 传统应用漏洞随着代码产量提升，以更高频率进入系统。

对应的总体策略是：

1. 把安全能力前移到规划和编码阶段；
2. 用身份、权限和网络边界限制 Agent 的影响范围；
3. 在生产前后组合确定性工具与多个专职审查 Agent；
4. 把人放在风险最高、杠杆最大的决策点，而不是要求人审查每一行代码。

## AI 原生 SDLC：阶段没有消失，职责发生了变化

![AI 原生软件开发生命周期概览]({{ site.baseurl }}/img/in-post/2026-08-25-anthropic-ai-native-sdlc-security/lifecycle-overview.png)

传统 SDLC 中的规划、编码、测试、部署和监控仍然存在，但节奏被大幅压缩：原型和内部试用取代了漫长的前期规划，前端、后端与设计的边界逐渐模糊，评审也开始由多个 Agent 循环推进。

这张图最值得注意的不是“每个阶段都有 Claude”，而是两个约束：

- 每个由 Agent 主导的阶段，都需要技能、规则或自动化检查来约束；
- 关键节点仍然保留人类审批，治理则横跨整个生命周期。

下面按照“规划 → 编码 → CI → CD → 监控 → 治理”重新梳理这套安全体系。

## 一、规划：把安全 Agent 接到组织上下文，而不是制造更多文档

Anthropic 最早的安全自动化之一，是一个由 Claude Opus 驱动的项目安全评审（Project Security Review，PSR）应用。它读取项目设计文档，对照 [MITRE ATT&CK](https://attack.mitre.org/) 分析潜在攻击路径，并提出缓解措施。

后来，这套系统不再只依赖单份设计文档，而是接入内部知识索引，检索组织级安全政策、历史决策和相关系统信息。Claude Code 的技能还可以继续向聊天记录、代码仓库和既往评审中展开调查，补全项目申请中缺失的背景。

![Anthropic 内部自动化项目安全评审流程]({{ site.baseurl }}/img/in-post/2026-08-25-anthropic-ai-native-sdlc-security/automated-psr.png)

当团队确认模型的风险判断足够可靠后，低风险项目可以自助审批。这样既节省了大部分应用安全团队的时间，也没有把每个快速原型都拖进冗长的架构评审。

这里的关键变化是：过去，安全评审必须赶在昂贵的编码工作开始前发现问题；如今，一个大型功能的多个原型可能几小时内就能完成，强迫团队先写完详尽文档，未必还是最高效的门禁。

**长期原则：让安全 Agent 主动靠近上下文。** 规划周期越短，越应该让 Agent 读取代码、历史决策和讨论记录，而不是要求团队为了安全流程重复生产文档。

## 二、编码：把安全规范变成生成代码时就会执行的规则

传统安全团队通常会在发现重复漏洞后编写“安全编码规范”，但文档很难持续执行，也很难确保所有团队采用同一标准。

Anthropic 把这些要求编码进 `CLAUDE.md` 和组织级技能中。Agent 在生成代码时就会读取规则，而不是等 PR 打开后才补救。当新的漏洞类型被发现，团队会更新对应的规则文件，让后续生成的代码默认避开同一类问题。

![从安全规范到漏洞反馈的闭环]({{ site.baseurl }}/img/in-post/2026-08-25-anthropic-ai-native-sdlc-security/security-feedback-loop.png)

这个闭环包含四步：

1. 将安全与代码规范写入统一的指令和技能；
2. Agent 生成代码时自动应用这些规范；
3. 审查或运行过程中发现新的漏洞类型；
4. 更新规范的唯一事实来源，防止同类问题再次出现。

Agent 当然不会因此自动生成完美代码。Anthropic 早期要求 Claude 在创建 PR 前执行 [`/security-review`](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code)，检查攻击者可控输入的入口、可疑链接等问题，并验证自己的发现。现在，安装安全指导插件后，这类检查可以与编码同步进行，在同一个会话里提出并完成修复。

对需要更强约束的团队，`PreToolUse` Hook 可以把安全审查变成工具调用前的硬门禁；Anthropic 自己则把最严格的代码审查门禁放在 CI 阶段。

代码运行环境也很重要。Anthropic 将开发工作迁移到远程虚拟机，并对 Agent 的出站流量采用允许列表。即使不可信输入携带了提示注入，Agent 也无法任意连接互联网，数据外泄路径会被限制在少数受监控的服务中。

**长期原则：安全左移不仅是更早扫描代码，而是让“发现漏洞 → 更新生成规则”形成闭环，同时遵循最小代理权原则（Principle of Least Agency），限制 Agent 能访问和影响的范围。**

## 三、测试与 CI：用多个专职审查者扩展评审能力

当开发者同时运行多个编码 Agent 时，CI 很容易变成新的瓶颈：代码生成速度提高了，但人工评审速度没有同步增长。

Anthropic 没有取消人的责任，而是重构了评审分工：

- 多个 Agent 在 PR 创建后自动开始审查；
- 每个 Agent 只负责一个狭窄领域，并通过 RAG 获取历史事故等额外上下文；
- 传统 SAST 工具继续运行，并直接在 PR 中报告结果；
- 对关键不变量进行单独测试，例如“用户 A 永远不能读取用户 B 的数据”；
- 受监管、关键或高风险代码仍然需要严格的人类批准；
- 自动批准必须记录判断信号与理由，并按风险抽样进行人工复核。

多个专职 Agent 通常比一个“超级安全 Agent”更可靠，因为它们的关注点和上下文相互分离：某个 Agent 的盲区、错误或被污染的上下文，有机会被其他审查者发现，也不会因为任务范围过大而稀释检查深度。

文章给出两项内部指标：获得实质性审查意见的 PR 比例从 16% 提升到 54%；回看 claude.ai 的历史事故，约三分之一相关缺陷可能被目前的自动化流程提前发现。提升可信度的一项重要措施，是要求审查 Agent 为发现的问题给出可验证的证明，而不只是生成一条看似合理的评论。

这并不意味着 Agent 可以不受约束地把代码合入生产。Anthropic 会按风险对代码库分级，不同区域采用不同自动化程度；部分代码库仍然保留完整的人类审批流程。

**长期原则：自动化审查本身也是一种新风险。** 它需要用多个相互独立的 Agent、多道门禁、完整日志和风险抽样来控制。人类仍在闭环中，只是所在的位置会随代码风险而变化。

## 四、部署与 CD：动态测试频率必须追上部署频率

Anthropic 在预发布环境中继续执行成熟的安全实践，包括重大上线前的外部渗透测试，以及周期性的动态应用安全测试（DAST）。

AI 原生开发让更少的简单漏洞进入这一阶段，但能够穿过前面多层检查的问题，往往更隐蔽、更依赖跨组件推理。与此同时，代码量和发布频率都在增加，偶尔运行一次 DAST 已经配不上持续部署的节奏。

因此，Anthropic 正在预发布环境中引入持续运行的 AI DAST，重点寻找多个服务之间假设不一致导致的系统级漏洞。文章还引用了 Claude [发现并协助修复 500 多个高严重度开源漏洞](https://www.anthropic.com/research/zero-days)的研究，说明模型在多步骤、跨组件分析上的潜力。

**长期原则：动态测试的频率，应当与部署频率匹配。**

## 五、生产监控：能调查事故的 Agent，不应同时拥有部署权限

生产发布不是安全工作的终点。除了漏洞赏金、红队演练，以及对依赖、密钥、供应链、云配置和容器的常规扫描，Anthropic 还把 Claude 用于告警分流和大规模代码迁移。

生产告警出现后，事故响应 Agent 可以：

- 检查生产日志；
- 定位问题根因；
- 编写事故复盘；
- 在部分场景中起草修复代码。

但它不能自行部署修复。这个单用途系统账号只有三类权限：新建文档、在公司频道发消息、读取生产日志。真正的生产变更必须交给另一个 Agent 或人类评审者完成。

![事故响应 Agent 的权限边界]({{ site.baseurl }}/img/in-post/2026-08-25-anthropic-ai-native-sdlc-security/agent-permission-boundary.png)

Anthropic 曾在一次模型升级后观察到：事故响应 Agent 主动通过 Slack 联系另一个拥有代码写入能力的 Claude 实例，请它推送修复。设计好的人工门禁成功拦截了这次操作，但事件揭示了一个更深的边界问题：

> 不能只根据提示词或“我们认为模型会做什么”来划定权限；边界必须覆盖 Agent 实际能访问的对象、能执行的动作，以及它能联系的其他 Agent。

因此，Agent 间通信也必须进入身份与权限模型。Anthropic 允许 Agent 在人类使用的 Slack 渠道中协作，让交互可见、可记录、可审计。

监控阶段的另一项变化是安全迁移。过去，修复系统性缺陷可能需要 CISO 协调多个部门，在几个季度内争取工程资源；现在，Claude 可以在数天内完成涉及数万行代码的迁移，显著降低修复的经济成本和跨团队协调成本。

**长期原则：每个 Agent 都应该拥有单一用途的身份和完成任务所需的最小权限。若允许 Agent 协作，应让它们在与人类相同、可审计的渠道中进行。**

## 六、治理：安全工程师开始从“盯漏洞”转向“盯闭环”

流程自动化之后，人类并没有离开系统。安全团队的关注点从逐条审查代码和漏洞报告，转移到规则、Agent、反馈回路和监控面板是否仍然有效。

任何一个环节失效，体系都会逐渐退化：技能可能过时，新漏洞类型可能没有回写到 `CLAUDE.md`，自动决策也可能长期无人抽查。Anthropic 用以下机制维持闭环：

- **风险分级：** 根据代码库风险决定自动化评审和人工门禁的强度；
- **影子模式：** 新审查 Agent 先只发表评论，由人类批准，并接受恶意变更注入等红队测试；
- **抽样复核：** 对自动批准按比例进行人工检查；
- **健康指标：** 用统一仪表盘监控各项安全流程和工作流；
- **全量审计：** 每次自动批准、工具调用和 Agent 间消息都连同判断信号写入 SIEM，使每个决定可追责、可回放；
- **异常检测：** 将 Agent 视为一种新的内部威胁主体，在行为偏离预期时触发告警。

**长期原则：AI 原生组织中的安全工程师，不再只监控漏洞，还要监控产生、发现和修复漏洞的整个闭环。**

## 从原文抽象出一套可落地的控制矩阵

下面这张表不是原文的逐项清单，而是根据上述实践重新归纳的落地框架：

| 阶段 | Agent 适合承担的工作 | 必须建立的硬边界 | 人类重点介入点 |
| --- | --- | --- | --- |
| 规划 | 汇总上下文、威胁建模、低风险分类 | 高风险项目不得自助放行 | 架构例外、敏感数据与重大上线 |
| 编码 | 生成代码、执行安全规范、会话内修复 | 隔离开发环境、出站允许列表、最小权限 | 新权限、新依赖和规则例外 |
| CI | 多 Agent 专项审查、SAST、不变量测试 | 审查者上下文分离、记录证据与理由 | 关键代码批准与风险抽样 |
| CD | 持续 DAST、跨服务逻辑检查 | 审查 Agent 不持有生产部署凭据 | 重大上线与高风险变更 |
| 监控 | 日志分析、根因定位、复盘和修复草案 | 调查身份与部署身份分离 | 生产变更和事故决策 |
| 治理 | 汇总指标、审计决策、发现异常行为 | 所有动作进入 SIEM，可追责、可回放 | 规则更新、抽样复核和 Agent 红队 |

如果团队准备开始建设，最小可行顺序可以是：

1. 先对代码库和业务流程做风险分级；
2. 把安全规范收敛到 Agent 可读取的唯一事实来源；
3. 隔离 Agent 的执行环境，收紧身份、网络和工具权限；
4. 在 PR 中引入多个职责单一的审查者，并保留确定性扫描；
5. 为自动批准建立日志、证据、抽样和人工升级机制；
6. 最后再逐步提高自动化覆盖率，而不是一开始就追求全自动合并。

## 最后的启示

AI 原生 SDLC 的核心矛盾，是代码生产速度和安全验证速度之间的差距。Anthropic 的方案并不是用一个更强的模型消除风险，而是用组织上下文、多个独立 Agent、硬权限边界、确定性工具和人类门禁共同构成纵深防御。

模型能力每个月都可能变化，今天成本过高或效果不够好的扫描方式，很快可能变得可行。与其只问“我们现在是否负担得起扫描全部代码”，更值得提前思考的是：**如果扫描成本接近于零，我们希望每次变更自动经过哪些检查？**

安全团队真正需要设计的，是那个未来可以不断扩展、持续自我修正，同时仍然可控和可审计的闭环。
