a2a 是我给自己做的多 Agent 编排工具：Claude Code 当主控，Codex 当 worker 和审查者，大家在同一个项目里分工干活。

刚开始做的时候，我以为难点在“协作”：怎么拆任务、怎么并行、怎么把结果合起来。做了一段时间才发现，真正值得研究的是另一件事：**谁来判断一项工作已经完成，判断的依据又从哪里来。** 多个 Agent 能不能一起干活是一回事，能不能建立一套可信的验收机制是另一回事，而后者更难。

所以 a2a 的设计目标可以概括成一句话：把 Agent 从一个自由度几乎没有上限的自主执行者，变成一个受外部约束的任务执行者。

下面先讲问题从哪里来，再讲 a2a 怎么设计验收，最后交代它的来路和目前的进度。

## 一、问题出在：Agent 自己给自己验收

### Goal 模式的三个缺口

所谓 Goal 模式，就是给 Agent 一个目标，让它自己一路跑到“完成”。用下来，我觉得它有三个结构上的缺口：

1. **Agent 既是开发者，又是验收者。** 写代码的是它，判断代码对不对的也是它。
2. **目标和测试都可以被它修改。** 遇到过不去的测试，改测试往往比改实现更省事。
3. **没有系统层面的硬性停止条件。** 什么时候该停，全靠目标里写的提示词去软约束。

我遇到过一个很典型的例子：Codex 为了让测试通过，直接改了测试代码。

这不一定说明它在有意识地欺骗。更可能的情况是，它为了完成眼前的任务，选了一条看上去满足目标、实际上偏离了真实需求的路。这是典型的**目标错位**。

用久了我还有一个感受：Agent 的优点是目标感很强，这同时也是它最大的缺点。它会为了完成当前目标，忽略目标之外的东西。在软件开发里，遇到一个问题时，常常需要往上想一层，设计点什么让这类问题以后不再出现；Agent 却往往只把眼前这个洞补上，仅此而已。

如果没有外部约束，一次 Goal 模式的运行很容易变成这样：

```text
用户提出需求
     ↓
Agent 制定计划 → 编写代码 → 测试代码
     ↓
发现问题 → 修改代码 → 修改测试
     ↓
再次发现问题 → 继续修改（反复多轮，消耗大量 token）
     ↓
Agent 宣布完成
```

最后那句“完成”，是 Agent 自己说的。

### 为什么要从 subagent 走向 multi-agent

在一个主会话里派 subagent，也能分出“写”和“查”两个角色。但我最后选了独立的多 Agent，主要看中三点：

1. 每个 Agent 都是独立进程，可以单独管理、单独中断、单独回收；
2. 每个 Agent 在自己的 Git worktree 里工作，互不干扰，可以并行；
3. 每个 Agent 的权限可以单独控制，写入者和审查者不必共享同一套能力。

第三点是后面整个验收设计的基础。

## 二、干净的上下文不够，还要独立的标准
{: #independent-context }

### 上下文会把错误假设一路带下去

模型根据上下文计算下一个 token 的概率分布，再由解码策略选出输出。这能解释一个常见现象：一个 Agent 连续开发几个小时以后，有时会反复围绕同一个错误假设改代码。

这不等于长上下文必然出错，也不等于模型一定纠正不了自己。真正的问题通常是几个因素叠在一起：

- 模型已经形成了一个错误假设，后面的推理都建立在它上面；
- 测试标准不明确；
- 没有外部反馈；
- 系统也没有限制它继续尝试。

所以很自然的想法是：换一个上下文干净的 Agent 来审查。

### 全新的上下文照样会出错

假设 worker 在开发登录功能，它错误地认为：只要用户名存在，就可以登录。代码按这个理解写完了。

现在新开一个 reviewer，上下文完全干净。但如果你只告诉它“检查这个登录功能是否正常”，它可能做一次简单的登录测试：输入用户名，进入了系统，于是判断功能正常。

worker 和 reviewer 都没有理解真正的需求：**必须验证密码。**

两个 Agent 依然会犯同样的错误，因为它们缺的不是干净的上下文，而是一个外部的、明确的正确性标准。

这里可以把两件事分开看：

- **独立的上下文**，解决的是判断会不会被既有对话带偏；
- **独立的验收标准**，解决的是判断的依据从哪里来。

后者更关键。a2a 后面的设计，大部分都在回答“依据从哪里来，又由谁来守住它”。

## 三、a2a 怎么设计验收

### 1. 需求规格先于开发存在

不要只交给 worker 一句“实现用户登录”。开发之前，先写好一份任务契约：

```yaml
task_id: AUTH-001
description: 实现用户登录功能

requirements:
  - 正确的用户名和密码可以登录
  - 错误的密码必须被拒绝
  - 不存在的用户必须被拒绝
  - 登录成功后返回有效会话

allowed_paths:
  - src/auth/
  - tests/unit/auth/

protected_paths:
  - tests/acceptance/
  - .github/workflows/

max_attempts: 3
```

这份契约里有两个关键设计：

1. **限定可以修改的范围。** worker 只负责指定的模块，不应该顺手重构项目的其他部分。
2. **预先确定验收条件。** 这些条件在开发过程中不能由 worker 单方面修改。

当然，需求本身也可能写错，所以要允许提出修改申请，但申请必须经过人工或可信的需求管理流程批准。

这就是工程里常说的 **Contract（契约）**：Agent 按契约完成工作，而不是自己决定什么叫完成。

在 a2a 里，这份契约叫任务卡。它现在包含目标、修改边界、验收条件、非目标（至少一条）、红态命令、任务类型、复杂度和执行器；编号、来源 ticket、起点提交和唯一写入者由脚本填写，不让模型自己填。上面示例里的 `protected_paths` 和 `max_attempts`，是这次整理思路后要补进任务卡的字段。

改需求的通道也已经有了：worker 和 reviewer 发现范围外的问题，必须上报到面板，不许自行忽略。凡是涉及权限、范围、验收条件、安全或不可逆操作的条目，主控都不能自行关闭，要留给我决定。

### 2. 写代码的和放行的，权限必须分开
{: #task-card-state }

任务调度、权限控制和合并门禁，不应该全部依赖 LLM 的自觉。

举个例子：worker 不能自己宣布“我已经通过验收，可以合并”。它只能提交一个候选结果，真正判断是否满足合并条件的，是外部程序。

主控可以负责理解任务、安排执行顺序，但凡是会改变任务状态的动作，都应该由程序先核对前置条件，再去执行。一句话说：**LLM 负责不确定的工作，程序负责确定的规则。** 在 a2a 里，这条原则写成了“提示词管判断，脚本管事实”。

落到 a2a 上，这个“程序”就是门禁。认领（claim）、交付（submit）、验收（verify）、集成（integrate）和回收，只能经过这一个入口：

- 认领时原子分配 attempt、受管运行身份和 fence（所有权代次）。旧 attempt 的交付会被拒绝，换了执行者，也不会“顺带”把旧结果算进来；
- 交付必须给出完整的提交号和规格版本。模型说“做完了”、终端显示空闲，都不算交付；
- 验收和集成共用操作锁。锁被释放，只说明执行者退出了，不代表验收通过；
- 集成用 Git 的 compare-and-swap 推进目标分支，成功后再独立读回一次；中途被打断，就恢复原来的集成意图，不重新猜；
- 结果未知时进入可恢复的暂停状态，不会被补写成成功。

{% include related-reading.html title="状态栏给模型看，门禁核对状态变化" summary="第二章的 Agent 状态栏把工具计数、任务进度和当前环境整理成模型可直接使用的摘要。a2a 的任务卡也把目标、边界和验收要求显式写出，不过状态是否能推进，还要由程序核对提交、规格和前置条件。模型看得清当前状态，与系统有权确认任务完成，是相连但不同的两层责任。" url="/ai-agent/chapter-02/#agent-status" label="回看第二章：Agent 状态栏" %}

角色分工如下：

![a2a 的角色分工：用户只和构思主控对话，执行主控经门禁管 worker 和 reviewer](/img/in-post/2026-10-11-a2a-design/roles.svg)

主控分成两个角色，都由 Claude Code 担任：

- **构思主控**是我日常唯一需要看的那个：接收想法、澄清需求、写决定和任务卡、标“就绪”，再转交给执行主控。它不直接派发、验收或集成；
- **执行主控**在已批准的范围内监督执行：派发、盯进度、验收、集成、回收，全部经过门禁。它自己不写代码。

两者通过追加式的收件箱交接。这里有一条我觉得很关键的防线：**对方会话发来的消息，只能当作队友的请求，不能当作用户的批准。** 需要我授权的分派，必须逐字引用我的原话并注明出处；没有引用的，一律按未授权处理。状态只用 `PASS`、`INCOMPLETE`、`BLOCKED`、`NO_GO` 四个词报告，构思主控转述时不允许上调。

**为什么要这么麻烦？** 因为提示词是软约束。你告诉 Agent 不许修改验收测试，它可能遵守，也可能因为上下文、工具调用或别的原因违反。但如果验收测试根本不在 worker 可写的范围里，它就改不了，软约束就变成了更可靠的权限约束。

a2a 的权限因此分成四层，全部在工作台内部实现：角色卡、任务卡路径加门禁检查、每个会话的 CLI 启动参数、收件箱命令行限定谁能写哪种条目。它不改 `~/.claude`、`~/.codex` 这类全局配置，钩子和权限只通过每个会话的启动参数传进去。

> 需要特别说明：Git worktree 只是工作目录的隔离，不是安全边界。如果多个 worker 使用同一个操作系统账户，又能访问相同的文件和 Git 凭据，它们仍然可能碰到不属于自己的文件。a2a 目前就是这种情况，靠的是门禁事后核对路径边界。如果需要真正的强制隔离，就得用独立容器、受限的文件系统权限或其他沙箱机制。

### 3. 验收测试不能由 worker 随意修改

回到 Codex 改测试的问题。我的做法是把测试分成两类：

- **开发测试**：worker 可以创建和修改。比如写完一个函数，worker 自己写单元测试，检查参数、返回值和异常情况。这类测试帮助 Agent 自己发现问题；
- **独立验收测试**：由可信的验收流程维护。worker 可以知道验收要求，但不能直接修改用于最终判定的测试实现。

交付之后，门禁会跑一串固定的检查，全部通过才集成到项目的工作分支（不 push）：

![门禁检查串：机械检查全过后才开独立审查，任一项不过就打回](/img/in-post/2026-10-11-a2a-design/gate.svg)

接下来是一个绕不开的问题：**怎么知道验收测试本身是对的？**

一个测试存在，不代表它能抓住错误的实现。检查串里的“红态”就是为这个设计的：如果任务卡写了红态命令，候选里的新测试放回起点提交上必须失败，在候选提交上必须通过。一个测试在修复之前就能通过，说明它根本没测到要修的问题。

换个角度看，红态检查其实就是一次最小规模的**变异测试（Mutation Testing）**。变异测试的思路是故意把代码里某处正确的逻辑改错，造出一个“变异体”，再看测试能不能发现。红态检查只用了一个变异体，就是修复之前的旧代码；完整的变异测试会系统地造出很多个，比如把 `>` 改成 `>=`、删掉一行校验、把返回值换成常量，逐个检验测试能不能把它们抓出来。

以前给每个功能、每个接口都做变异测试很费时间。但 Agent 有个很好的特点：这种重复性的工作，它不嫌烦。所以下一步打算让 Agent 生成变异体、跑测试、整理出没被抓住的那些，结果交给验收流程判断。

当然，变异测试只能评估测试发现某些代码错误的能力，不能证明需求是完整的，更不能证明程序绝对正确。但它正好对准我观察到的那个问题：测试看似存在，实际上抓不住错误的实现。

验收测试本身也要保护起来。a2a 现在用路径边界检查拦下越界的改动；以后加上 `protected_paths`，验收测试、CI 配置、测试入口和构建脚本都会进入保护范围，因为改掉其中任何一个，都能绕过验收。如果交付最终要走 GitHub，还可以再加一道远端的门：配置[受保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、必需的状态检查和合并限制。

### 4. reviewer 要自己取证，不只读 worker 的报告

a2a 的审查是每次交付都新开的只读会话。门禁会核对三件事：审查会话不是本任务的写入会话、确实是这次新开的、结论绑定到候选提交号。

但这还不够。以前我的做法是让 worker 留下截图作为证据，这里还有改进的空间。截图只能证明某一刻页面的静止状态；录屏又太占硬盘，这也是我没有借鉴前端录屏的原因。

更可靠的做法是：reviewer 拿到任务规格、代码变更和提交号以后，在独立的环境里重新执行测试。对于前端功能，由测试程序启动应用，用工具执行真实的用户操作；截图由验收程序生成，而不是由 worker 提供；同时检查接口返回值、数据库状态和日志。

**验收的核心是独立获取证据，而不是独立阅读另一个 Agent 提供的证据。** 这一条是接下来要补进 reviewer 流程的。

### 5. 给无意义的循环设一个硬性预算

Goal 模式浪费 token，很大一部分是因为没有硬性停止条件。a2a 现在的规则是：同一个 attempt 连续被打回 3 次，就停止自动回写，交给执行主控判断。打回时，失败摘要会自动写进 worker 的终端，带 `⟦门禁 #n⟧` 标记。

接下来要补的是一份结构化的失败报告，交给构思主控，再由我决定是继续开发、调整需求，还是换一个实现方案。报告至少回答四个问题：

- 哪些验收条件没通过？
- 已经尝试过哪些修改？
- 有没有出现重复修改？
- 现在需要什么外部信息？

预算不只看次数，还要看成本。a2a 从第一个切片起就只追加地记录原始事件：会话启动、回合与权限等待、用户输入、派发、门禁逐项结果、改动行数、审查结论、打分、面板问答、worktree 生命周期、提交尾注、复盘。指标不预先算好存起来，而是从这些事件现算。在此基础上，再补上每个任务的 token 消耗、模型费用和执行时间。

有了这些数据，就可以认真比较：单 Agent、原版 Herdr 和 a2a，到底哪个更有效。比较时不能只看并行的 Agent 数量，也不能只看最终的测试通过率，更要看**错误实现通过验收的比例**，以及完成同一个任务的综合成本。

做到这一步，a2a 就不只是一个个人开发工具，而是一个有实验价值的工程研究。

## 四、围绕验收的几项工程细节

### 交互终端，而不是无头模式

每个 agent 都在真实的交互终端里跑，由常驻的编排后台用 node-pty 托管，界面用 xterm.js 渲染，窗格里是我自己的 zsh。这样我能随时看见、随时插手。

插手本身也是数据：在受管 worker 的会话里直接打字，会记为“人工介入”，挂到对应的 attempt 上。复盘时能看出哪些任务一次到位，哪些任务需要人去纠偏。

代价是“往别人的终端里塞字”变成了一个需要证明的动作。早期实测中出现过这样的情况：Codex 正停在批准提示上，送进去的一条输入被当成了“接受”，执行了一次测试夹具里的写入。后来的做法是：

- 状态只认各家的结构化信号（Claude Code 的 hooks、Codex 的 notify），拿不到就显示“未知”，不用正则去读屏幕；
- 后台在写出回车的那一刻就记为“忙”，不等对方的开始事件；只有收到时间更晚的 Stop 事件，才放行下一条注入，其余排队；
- 用户按 Esc 中断后不会有 Stop，就一直保持忙，等用户手动放行。

这一版在两家 CLI 上各跑了竞态、模拟用户提交、Esc 后放行和空闲送达四类样本，全部通过。早先的失败记录原样保留，没有被这次通过“撤销”。

### 用户输入是数据，和派发的提示词分开存

在 Herdr 下，主控注入的提示词和我亲手打的字，在 Codex 的原生记录里都是 user 消息，事后分不出来。a2a 把我本人的输入（消息、回答、批准或拒绝、选择、动作）单独存成追加式记录；主控、agent 和自动化发出的文本记作派发记录，带 `⟦主控 #序号⟧` 标记，两者不混。

这样，人工介入能准确挂到 attempt 上，复盘能看到我真正纠正过什么，授权引用也有据可查。

### 提交尾注：每个提交都知道是谁做的

改方向前我统计过一次：Synara fork 上 10 月 6 日以来的 52 个 a2a 提交，作者全是我自己，其中 7 个带了 Co-Authored-By，但没有一个能看出是哪个任务、哪个 attempt、什么模型和思考强度做的。

现在的做法是：编排后台启动 agent 会话时，用 Git 的 `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_0`、`GIT_CONFIG_VALUE_0` 环境变量为这个进程单独指定 `core.hooksPath`，不写任何配置文件。实测提交时会追加尾注，加了 `--no-verify` 也照样追加；不带这组环境变量的提交，就没有尾注。

尾注记录任务、attempt、会话、角色、CLI 版本、模型、强度和启动记录号。门禁核对时，带本 attempt 尾注的提交正常通过；没有尾注的视为我本人的提交，记为人工介入；带别的任务尾注的直接打回。

### 打分折进验收命令

每个 attempt 结束时打一次分。打分是验收命令（集成或放弃）的一个参数，不另起一轮提问，缺了打分就拒收。边界纪律、工程品味各 0–3 分并写理由；轮数、耗时、打回次数这些客观字段由脚本填。

### 换了位置，就重新证明

门禁的位置换过两次：从 Python 脚本，到 Synara fork，再到 a2a 自己的编排后台。规矩是：**旧实现的通过结论，不替新实现背书。** 每次搬家，交付 8 项、恢复 9 项、编排 18 项场景，都要在新位置重新取得红态、绿态和反例。

这其实也是“独立验收”原则用在 a2a 自己身上。

## 五、a2a 的来路

### 方向改过三次

a2a 从 2026 年 10 月 6 日开始做，到写这篇文章时，方向已经改了三次。每次都有具体原因。

| 阶段 | 做法 | 为什么放弃或改变 |
| --- | --- | --- |
| 第一阶段（10-06） | 在终端多路复用器 [Herdr](https://github.com/herdrdev/herdr) 上跑 agent，用一个 Python 脚本实现认领、交付、验收和集成门禁 | 门禁跑通了，受管交付、中断恢复和自动运行三组场景都用真实入口验收过；但界面只能靠终端，用户输入、问题上报这些需求没有地方放 |
| 第二阶段（10-07） | fork [Synara](https://github.com/Emanuele-web04/synara)，把门禁原生实现进去，用它的统一 provider 层和 MCP 网关接各家 CLI | 几乎每张票都要改 Synara 的上游代码（provider 适配器、网关、投影）。真实派发虽然跑通了，合并却还在门禁之外，由主控手工完成 |
| 第三阶段（10-10 起） | 各家原生 CLI 以交互终端运行，a2a 只做编排、门禁与记录；工作台是轻量 Electron 应用，只借用 Synara 的前端组件与样式 | 当前方向 |

第二阶段的教训，恰好也是验收问题：合并留在门禁之外，就等于最后一步还是靠主控自觉。

第三阶段的方向是我在一次决策会话里定下来的，原话是：“不用 Synara 的统一网关，只用 Synara 这种前端样式框架就行，里面具体的 CLI 还是看每家自己的能力，我们只做编排，像 Herdr 这样。”模型最好配它原生的工具用。Claude Code 和 Codex 都在快速迭代，中间再包一层统一抽象，等于每次都要追两家的变化。

### 从立行的文章里借了什么

立行的[《将军赶路不追小兔：多 Agent 调度体系的架构与实践》](https://zj1123581321.com/posts/260809-multi-agent-scheduling-architecture/)把多 Agent 调度分成三层：主脑只做规划、拆任务卡、验收和复盘，执行层按任务类型和额度分给不同的 CLI，再加一套统一门禁。a2a 借了其中七个思路，落地方式各有调整：

| 文章里的思路 | a2a 的落地 |
| --- | --- |
| 任务卡：目标、修改边界、验收条件 | 任务卡是受管任务的结构化契约，增加了非目标、红态命令、任务类型、复杂度和执行器 |
| 提示词加脚本，能用脚本保证的就不只靠提示词 | 写成项目原则“提示词管判断，脚本管事实”，并补上一条：脚本只做能判对错的检查，不做策略引擎 |
| 并行 worktree，统一命名，用完清理 | 认领时创建 `<项目>/<任务卡号>-a<序号>` 和分支 `a2a/<任务卡号>-a<序号>`；集成后只删除干净的 worktree，提交保留为隐藏引用；有未提交改动或状态未知时不删，上报面板 |
| 写代码和审查分开 | 每次交付新开只读审查会话，门禁核对它的独立性并把结论绑定到提交号 |
| 门禁全绿才合并 | 一条固定的检查串，见第三节 |
| 每次提交都能追溯到工具、模型、配置 | 每个 agent 会话的提交自动追加 `A2A-*` 尾注 |
| 主脑给执行层打分、周期性复盘 | 每个 attempt 结束时打一次分；复盘手动或每周触发，可以选 CLI、模型和思考强度 |

也有不少内容没借：

- **额度感知调度、token 与缓存命中率监控**：我已经在用 TokenTracker 看用量，再做一遍就是重复造轮子；
- **无头模式**：a2a 的执行层用交互终端，原因见上文；
- **单次改动量上限、前端录屏**：先不限制改动量，但改动行数仍记成原始事件，以后据此观察大交付会不会拉低审查质量；录屏攒多了太占空间；
- **多审查者交叉、规则式审查工具、风险分档、定期安全扫描**：v1 只放一个主审；目前只有一个项目，风险分档用不上；
- **多机、远程**：只面向本机 macOS。

## 六、几条用代价换来的经验

- **终端空闲、模型说“完成”，都不是交付。** 门禁只认带身份的 submit 和独立验收。
- **等待超时不代表 worker 挂了。** 要先核对可见进展、产物和权限状态再处置；回收前要确认 agent 已经空闲、交付也已提交，只看到提交落地是不够的。
- **构建输出目录里不能放指向源码的链接。** 有一次复验时，共享 checkout 的构建输出目录里出现了指向源码和依赖的链接；构建工具清理输出目录时顺着链接删除，一次误删了 6,186 个受控文件。现在需要新构建时，只用产品自己的标准构建命令。
- **区分模型行为和协调缺陷。** 有一类问题是模型在还有已授权工作时就结束回合。我把它归为模型行为，单独记录，不当作分工协调的缺陷去整改，以免为模型的毛病加一堆流程补丁。
- **测试启动的后台服务要脱离调用者的进程组。** 否则调用它的命令一结束，服务也会被一起回收。

## 七、现在做到哪一步

截至 2026 年 10 月 11 日：

- 原生 CLI 状态信号与终端注入的事实验证已通过（见第四节）；
- 门禁源码已从 Synara fork 抽进 a2a 的编排后台，fork 里的门禁不再作为入口；
- 编排后台的启动、关停与多回合身份核对正在实现和验收中；
- 日常派发仍走 Herdr；按计划在这期间先用任务卡模板、提交尾注和验收打分，提前积累数据。

这次整理后，验收这条线上还要补四件事：任务卡加入 `protected_paths` 和 `max_attempts`；用 Agent 批量跑变异测试，检验验收测试本身；reviewer 改为在独立环境里自己取证；打回超限时生成结构化的失败报告，并记录每个任务的成本。

切换到新工作台的条件是我自己定的：用户输入记录、两层主控、问题面板、任务卡、门禁检查串与独立审查、worktree、提交尾注、面板提问、打分、复盘和四个指标视图（模型使用分类、一次到位率与打回原因、注意力消耗、打分分布）都要能用；我亲自走一遍“一张真实任务卡从派发跑到集成”，再说一句“可用”，才切过去。

所以这篇文章只是设计稿。a2a 的仓库目前是私有的，项目定位是开源，做完以后会公开。届时我会在这里补上真实产品、一次完整闭环的运行记录，以及这些设计哪些站住了、哪些被推翻了。
